# 产品决策 log

## 2026-07-25 · 代金二分：自用券 / 分发券

### D-P1-4 产品二分（大股东确认）

- **决定**：代金体系拆成两类，**创建时二选一**，**核销时扫码自动分支**（店员不再选手动账本）。
  1. **自用券**  
     - 场景：集团/本店自用预付；**同企业下多门店可共用**（非全网开放互核）。  
     - 资金：**售出即归经营主体**（现金或店收）；**平台不做 Transfer / 不进可用·冻结·提现**。  
     - 奖励：**无**卖券佣金。  
     - 核销：记 **门店 + 金额/张**，只销权益，**不再分账入账**。  
     - 分店清算：靠 **核销报表** / 集团内部处理；**不做**「核销时自动转账」（无冻结池、易已提现、对账难）。  
  2. **分发券**  
     - 场景：分享、渠道、活动、抽奖等对外分发。  
     - 资金：维持现方案——**平台托管 → 核销分账 → 冻结 T+1 → 可提现**。  
     - 可配置佣金 / 奖池等。  
- **命名**：对外/店员统一 **自用券 · 分发券**（内部枚举建议 `self_use` / `distribution`）。  
- **抽奖**：见 **D-P1-6**（独享券 / 共赢券）；与代金二分对称，**不**再写「抽奖只挂分发」。  
- **UI 原则**：简单明了、美观大方；类型用 **强标签**（色+字）；账户中心 **两套数字分开**，禁止混成一个「余额」。  
- **不做什么（默认）**：自用核销自动 Stripe 转账；自用进 Token 可用/冻结；创建时模糊类型。

### D-P1-5 页面与心智（配套 · 代金）

- **创建**：第一步强制选类型，对比一行说明「钱在哪 / 谁能核 / 有无佣金」。  
- **核销台**：统一扫码 → 展示大标签「自用」或「分发」→ 一键确认；成功文案区分「已核销（无二次入账）」vs「收入已入冻结」。  
- **账户/经营**：自用看「今日售出（已收款）+ 待核销 + 分店核销」；分发看「可用 / 冻结 / 提现」。  
- **详细 UI 规格**：`docs/roles/product/ui-voucher-dual-type.md`。

## 2026-07-25 · 抽奖二分：独享券 / 共赢券

### D-P1-6 抽奖与代金对称的资金心智（设计确认 · 待实现）

- **决定**：抽奖也拆成两类，**与代金「售出即收款 vs 平台托管」同一骨架**，仅玩法多「即时小奖 / 大奖池」层。创建时二选一，核销扫码自动分支。

#### 1. 独享券（抽奖 · exclusive）

| 维度 | 规则 |
|------|------|
| 场景 | 本店/集团自己搞的「买券抽奖」：先收钱再核销余额 |
| 跨店 | **同企业集团门店**可核（与自用券一致）；非全网互核 |
| 收款 | **售出即归店**（现金柜台主路径；可选店收 PayNow） |
| 平台转账 | **不做**；不进可用/冻结/提现 |
| 卖券佣金 | **无** |
| 核销 | 记门店 + 扣余额；**不**再 `applyRedeemSplit` 入平台钱包 |
| 即时小奖 | **可有**；成本由 **店/集团承担**（售出款已在店）；系统记中奖结果，不从平台奖池扣 |
| 延迟大奖池 | **默认关闭** 或仅 **本店/集团本地展示奖**（不走平台 20% pot 进池）；避免「钱已提现却还要给平台池」 |
| 对账 | 今日售出（已收款）+ 待核销权益 + 中奖记录；与平台钱包分栏 |

#### 2. 共赢券（抽奖 · co_win / 现网主路径）

| 维度 | 规则 |
|------|------|
| 场景 | 分享、渠道、跨店、平台活动；顾客平台支付 |
| 跨店 | 入网互核（可跨企业，现规则） |
| 收款 | **平台托管**（Checkout / PayNow） |
| 结算 | 核销 → 分账 → **冻结 T+1** → 可提现 |
| 卖券佣金 | **可有** |
| 即时小奖 | 现规则（购后抽，平台活动配置） |
| 延迟大奖池 | 核销 pot 进池（如 20%），现 Model A |
| 对账 | 进账户中心可用/冻结；与独享栏分开 |

#### 3. 命名与内部枚举

| 对外 | 代金对照 | 内部建议 |
|------|----------|----------|
| **独享券** | ≈ 自用券 + 抽奖玩法 | `productKind=self_use` + `play=draw` 或 `drawExclusive` |
| **共赢券** | ≈ 分发券 + 抽奖玩法 | `productKind=distribution` + `play=draw` 或 `drawCoWin` |

店员话术两句：

> **独享券**：钱当场进店，集团能核，抽奖成本店里出。  
> **共赢券**：网上付平台，核销才进账，奖池大家一起做大。

#### 4. 与代金统一矩阵（店员只记「钱」+「玩」）

|  | 售出即收款 · 无平台结算 | 平台托管 · 核销结算 |
|--|-------------------------|---------------------|
| **无抽奖** | **自用券** | **分发券** |
| **有抽奖** | **独享券** | **共赢券** |

核销台仍 **一个扫码入口**；标签组合例如：`独享·抽奖` / `共赢·抽奖` / `自用` / `分发`。

#### 5. 独享券 · 奖池与资金（铁律）

- **禁止** 默认「核销 20% 进平台大奖池」——售出款不在平台，无冻结池可扣。  
- 若要集团内大奖：二期可做 **集团本地奖池记账**（报表+人工兑奖），不走 Stripe Transfer。  
- 即时奖：发券/购后可抽；兑奖登记在账号；实物/店内抵扣由店执行。

#### 6. 不做什么（默认）

- 独享券核销自动平台转账  
- 独享券与共赢券共用一个「奖池进度」数字不加标注  
- 创建时模糊「算独享还是共赢」

#### 7. 实现顺序（确认设计后再开工）

1. 数据模型：抽奖活动 `productKind` / 玩法标记与独享发券 API  
2. 核销分支：独享 = 自用同路径 + 抽奖展示  
3. 创建 UI：选「独享/共赢」再进抽奖模板  
4. 柜台发独享（现金）+ 大短码  
5. 老板双区：独享售出/待核 vs 共赢结算  
- **UI 规格**：`docs/roles/product/ui-draw-dual-type.md`

### D-P1-7 页面与心智（配套 · 抽奖）

- 与 D-P1-5 同原则：类型先选、标签强、账不混、成功文案分叉。  
- 创建抽奖：**独享** 强调现金/柜台；**共赢** 强调链接/PayNow/奖池。  
- 消费者：独享可短码到店；共赢走购券页抽奖体验。

## 2026-07-19 · 消费者站 vs 商家站分离

### D-P1-3 入口分离

- **决定**：
  - **`/` = 消费者站**（默认）：买券抽奖叙事 + 用户注册/登录；**无**「我是消费者/商家」双 Tab。
  - **`/for-business` = 商家站**：入驻、发券、后台入口。
  - 消费者首页 **页脚** 一行链到商家站即可。
- **原因**：双 Tab 把「浏览身份」和「登录会话」缠在一起，商家登录点「免费注册」会被 middleware 踢回 `/business`。
- **规则**：商家会话下点用户注册/登录 → 先 `logout?next=用户注册/登录`。

## 2026-07-19 · 试点产品边界（大股东确认）

### D-P1-1 代金券 vs 抽奖：各是各的

- **决定**：
  1. **S$10 代金券** = 纯「折扣代金券」活动（`voucher_discount` / `voucher_sale`），**无抽奖**。
  2. **抽奖活动** = 独立「梦想大奖池」（`draw_standard` / `lucky_draw_v2`），购券面额为 **三档：S$50 / S$100 / S$200**。
  3. 两条活动 **分开创建、分开链接、分开购买、分开对账**。
- **不做什么**：不为了试点把 S$10 塞进抽奖三档；不把三档抽奖拆成「3 张纸质券」语义。
- **账目验收**：大股东各买 **1 笔 S$10 代金** + **1 笔抽奖任一档**，核对实付 / 余额 / 核销分账 / 奖池。

### D-P1-2 抽奖「3 档券」定义

- **决定**：**3 档 = 三种购券面额**（50 / 100 / 200），不是 3 个大奖名称。  
  大奖展示（iPad / iPhone / BYD 等）是奖池 UI，与档位无关。

## 2026-07-18 · I0

### D-P0-1 企业 vs 门店信息架构

- **决定**：企业账号进 **公司 Dashboard**；具体店务进入 `/business/stores/[id]`；**无全局「当前门店」切换**。店员账号绑定店，登录即本店。  
- **原因**：符合真实连锁组织；减少错误核销记错店。  
- **复盘**：试点店员是否需要更短路径（桌面书签到 scan）。

### D-P0-2 I0 范围

- **决定**：只保证 **注册 → 设置 → 门店 → 码/核销选店**；发券/抽奖「能点开不崩」即可，不深打磨。  
- **原因**：市场演示卡在 onboarding 比卡在奖池配置更致命。  

### D-P0-3 完成定义

- **决定**：完成 = `acceptance.md` 全绿，不是「合并了很多 PR」。
